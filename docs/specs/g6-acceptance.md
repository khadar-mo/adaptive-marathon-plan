# G6 FitnessSnapshot and benchmark validation

## Acceptance evidence

1. **Requirements.** Master v1.0 Part A §§1, 11.3, 12–14 and T14/T15/T21 govern the fitness update and evaluation records. Parts 2–4 define the planner interface. The immutable artifact contains the multidimensional G5 state, raw and canonical provenance, code and configuration versions, policy and missingness, per-run actuals and a revision comparison.
2. **Scope.** G6 consumes the existing G1–G5 implementations and the dated source history from #45. Its SQLite tables are additive. Older G5 captures remain readable and replayable. A persistent Strava analytics feed is unavailable under #33. Provider attempts retain the particular capability, mode revision, terminal status and fallback cause actually recorded.
3. **Update path.** An import, source decision, raw receipt, QC/extraction selection, annotation, context/configuration revision or terminal provider result queues an event inside its own transaction. A running app checks committed events every 15 seconds. The worker establishes the current processing inventory, refits the snapshot from its inputs and records the snapshot and processed watermark together. A crash rolls back the partial refresh. A restart retries pending input. Background work waits for an active import, uses one SQLite writer, and never contacts a provider. An unchanged watermark returns its existing snapshot. New rules register a version; an explicit configuration selection retains its event key, actor, reason and timestamp. Changes to an already linked outcome append a revision. An updated recording or QC selection may require the runner to identify the new outcome explicitly.
4. **Fixtures.** Synthetic FIT SDK recordings exercise a 5,000 m run with 1,500.375 elapsed seconds, a summary written before the derived finish, calibrated intensity, fractional metres and London’s 25-hour day. Tests cover version reselection, a delayed insertion, ambiguous event time, unowned raw bytes after rollback, a provider outage and recovery, and a newly discovered shared recording. Training and outcome use different whole workouts. Common-set examples include a missing method, duplicate identity and exact fractional times.
5. **Tests.** Run `python -m pytest -q tests/test_validation.py tests/test_validation_browser.py` and the full suite. Assertions cover the unchanged pre-outcome prediction (T14), preserved raw hash and new selection after correction (T15), and distinct QC/configuration versions (T21). The API checks repeat a fixed T/K refit and compare every rebuilt value against saved inputs. The restart test starts the normal app after a committed import and waits for its scheduled snapshot without a manual capture request.
6. **API inspection.** `POST /api/snapshots` accepts `as_of`, `knowledge_cutoff`, `mode` and an optional `config_version`. `GET /api/snapshots/{id}` exposes the state. Its `inputs`, `planner`, `observations`, `activities/{activity_id}`, `compare/{previous_id}` and `replay` routes expose the precise evidence. `POST /api/snapshots/refresh` drains pending work. `POST /api/validation/predictions` freezes a named target, scheduled start, explicit source choice and model settings. Append an observed source effort through `POST /api/validation/predictions/{id}/outcomes`. `GET /api/validation/backtest` reports stored errors. `POST /api/validation/backtest` accepts a batch of historical cases, refits their declared T/K, freezes each recipe and then evaluates the supplied outcomes. The coordinator independently compared 28 joined run rows and seven weekly totals, checked two cutoffs and three model windows, and inspected a legacy processing gap, ownership of a compressed recording, and a genuine failure/retry through the real app. No personal values are included here.
7. **UI inspection.** Open **Fitness snapshots and benchmarks** from the fitness profile. Select a historical snapshot, inspect raw ownership and the source parser, compare revisions, schedule a target, choose a source effort, record a later outcome and inspect method errors and exclusions. The Chromium test uploads a physical synthetic FIT, inspects fractional elapsed seconds, schedules a fractional-distance benchmark, replays its frozen forecast and checks the layout at 390 and 1280 pixels.
8. **Lineage and replay.** T is the cutoff for events and K is the cutoff for knowledge. As-known reconstruction requires K=T. Event-time reconstruction permits later K. C is the actual artifact creation time. Method selection at C never establishes what was selected at historical T. The source ledger dates acquisition and ownership independently, retaining uncertainty for undocumented legacy knowledge. A date-only measurement has a local-day interval. When the day extends beyond T and its receipt is later than T, it remains visible as uncertain evidence outside the calculation. A forecast saved before a scheduled start also has to predate the actual workout start. Frozen G2 geometry, QC, source group, provenance, exponent, window, configuration and missingness remain inspectable. Replay reads saved inputs and checks code identities; a different implementation reports that the recorded version is required. A later shared raw recording or alias can disqualify a training/holdout pair, or reduce two previously distinct outcomes to one independent workout. Prior ledger entries remain intact.
9. **Manual and scientific limits.** On 26 November 2026 the runner attested that all **ten** original Garmin activities and highlighted trace cases in the project G0–G2 manual comparison matched, with no discrepancies reported. The project record in #15 tracks this scoped acceptance. It does not apply a manual pass to arbitrary database rows or other imports. The fitness outputs carry separate physiological, personal predictive and planning authority states. No calibrated personal interval, acceptable error, minimum N, or repeated-underperformance rule has been established. CS remains a diagnostic. Only attested qualifying races or controlled/rested maximal trials enter validation; an ordinary run never supplies the missing maximal result.
10. **Review and CI.** The worker exercised a pre-scheduled 300 s prediction and a later 320 s synthetic trial. For both methods, common N=1, MAE 20 s, signed bias −20 s and MAPE 6.25%. The coordinator’s independent real-clock synthetic trial scored a 100 s forecast against 96 s, producing MAE and bias +4 s and exact MAPE 25/6%. Personal predictive validity remains unestablished. The pull request records independent review and the required GitHub check for the merge head.

## Scoring

The direct comparison is the most recent qualifying whole workout at the target distance inside the recorded G4 window. Riegel uses the selected qualifying source and versioned G4 exponent; both methods can report an unavailable reason. Forecasts never use the held-out run’s other segments as training inputs. Compare prospective forecasts, historical as-known reconstructions and later-knowledge reconstructions separately.

For the same eligible outcomes, MAE is the mean absolute predicted-minus-actual elapsed time, bias is that signed mean, and MAPE is 100 times the mean absolute error divided by the respective actual time. Positive bias means the prediction was longer. Results retain exact rational values, distance, provenance, method configuration, forecast horizon, missingness and common N. With N=0 the metrics are null. Each stratum lists excluded outcomes and missing methods, with an exact-horizon breakdown for repeated comparable outcomes.
